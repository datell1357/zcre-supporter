# ZCRE 서비스 영향 재검토

> 이 문서는 0.2.8 당시의 발견 사항을 보존한 기록이다. 대량 이력 재감지, 수동/공개 상태 요청 간격, 캐시와 오류 재시도는 0.2.9에서 수정했다. 최신 동작·검증·미해결 서버 조건은 [0.2.9 최적화](OPTIMIZATION-0.2.9.md)를 참조한다.

검토일: 2026-10-26 · ZCRE 서포터 0.2.8 (10)

## 판단과 범위

앱이 자동으로 실행하는 명시적 API 경로는 작업 목록·작업 상세·잔액·공개 서비스 상태의 조회다. 생성, 결제, 작업 취소·삭제를 자동 요청하는 코드는 발견하지 않았다. 다만 **조회 전용이라는 사실이 서버 부담이 없음을 뜻하지는 않는다.** 1,000대 동시 접속 전에는 아래 요청 증폭·재시도 문제를 해결하고 ZCRE 운영팀과 API 제한 및 서버 비용을 확인해야 한다.

이번 변경은 한국어 주석과 로컬 효과음·음량 설정이다. 작업 5초, 잔액 60초 및 상태 전이 후 15초 확인, 공개 상태 60초라는 기존 정책과 HTTP 실행 코드는 바꾸지 않았다. 효과음은 번들 WAV 두 개를 AVAudioPlayer로 재생하며 네트워크 호출, 오디오 다운로드, 별도 재생 폴링 타이머가 없다. 숨김·잠자기·음소거·0% 음량에서 재생을 중단한다. 오디오 출력 중의 CPU·전력 증가량은 계측하지 않았다.

검토 대상은 앱 소스·브리지·로컬 테스트·패키징 스크립트다. ZCRE 서버 코드, 운영 로그, DB 비용, 전체 웹 페이지의 실측 트래픽, 서버 허용량은 접근·측정하지 않았다. 테스트의 fetch는 모두 모의 응답이며 운영 서버 부하 시험이나 과금 작업을 실행하지 않았다.

## 확인된 보호 장치

- 브리지 실행 출처를 ZCRE HTTPS 두 호스트로 제한한다. 요청 경로는 잔액과 작업 조회 허용 목록이며 `GET`, `same-origin`, `redirect: error`를 사용한다. 토큰은 JavaScript 실행 범위에만 있고 네이티브로 반환하지 않는다. 근거: `Sources/ZCREBunny/Resources/ReadSnapshot.js:3`, `Sources/ZCREBunny/Resources/ReadSnapshot.js:42`.
- 비동기 응답 사이의 계정·세션·조직 변경을 확인한다. 새 계정에 이전 작업 ID나 잔액 캐시를 넘기지 않는다. 작업/잔액 응답을 검증하고 실패를 0개·0 크레딧으로 표시하지 않는다.
- 정상 계정 조회는 중첩하지 않으며 실패 시 30초부터 최대 300초까지 지연한다. 서버의 재시도 시간을 반영한다. 브라우저 조회 20초·네이티브 대기 25초 제한, 반복 페이지 커서 차단, 목록 최대 20페이지 제한이 있다.
- 오프라인·Mac 잠자기에는 앱 계정 조회를 취소한다. 공개 서비스 상태는 현황판이 닫히면 주기와 진행 요청을 취소한다. 지크 숨김은 데이터 감시를 중단하지 않는다.
- 진단은 사용자가 지정한 로컬 파일에만 저장한다. 자동 업로드는 없다. 알림 이력은 최근 30개이며 계정·작업 원문 ID 대신 해시를 저장한다. 프롬프트·인증 토큰·결과 URL은 네이티브 스냅샷과 진단에서 제외한다.

이 보호 장치는 앱이 직접 제어하는 경로에 대한 것이다. 로그인 창에서 사용자가 웹 서비스를 조작하거나 Clerk SDK·웹 페이지가 자체적으로 보내는 인증/페이지 요청까지 GET 전용 또는 동일한 5초 제한이라고 보장하지 않는다.

## 배포 전 우선 검토 사항

### 1. P1 — 최근 종료 이력이 50개를 넘으면 불필요한 잔액 재조회가 반복될 수 있음

근거: `Sources/ZCREBunny/Resources/ReadSnapshot.js:113`, `Sources/ZCREBunny/Resources/ReadSnapshot.js:132`.

상태 변경 비교에는 이전 작업 목록을 사용하지만 종료 이력은 50개만 보관한다. 최근 60초 겹침 범위에 종료 작업이 50개보다 많으면, 보관에서 빠진 작업을 다음 응답에서 다시 볼 때 새 작업으로 판정한다. 그러면 실제 전이가 없어도 잔액 재조회와 15초 후속 확인 기간이 반복해서 열린다.

모의 조건: 최근 종료 60개와 더 오래된 20개, 최근 50개를 이미 보관한 상태에서 5초 간격 6회 조회. 결과는 **목록 24회 + 잔액 6회**였다. 현재 사용자의 계정에서 상시 발생한다고 확인한 것은 아니다.

권장: 화면 표시용 목록과 변경 판별용 ID·상태 기록을 분리한다. 늦게 나타나는 작업과 빠른 완료를 놓치지 않는 보존 범위를 정하고 계정 전환 때 초기화한다. 잔액을 무조건 느리게 조회하는 방식으로 해결하지 않는다.

### 2. P1 — 공개 상태에 재시도 대기와 사용자 재요청 간격 제한이 없음

근거: `Sources/ZCREBunny/ServiceStatusStore.swift:45`, `Sources/ZCREBunny/ServiceStatusStore.swift:64`.

창을 계속 열어 둔 상태의 주기는 60초지만 재개방은 30초 이상 또는 오류 상태이면 즉시 조회한다. 수동 갱신은 진행 중 요청 하나만 막는다. 429/503 응답의 Retry-After나 오류 백오프는 없으므로 오류 중 창 재개방·새로고침을 반복하면 서버가 요청한 대기 시간을 따르지 않는다. 닫기에서 취소해도 이미 서버가 처리한 요청 비용은 사라지지 않는다.

권장: 공개 상태 전용 다음 허용 시각, 오류 백오프, Retry-After를 두고 수동·자동·재개방 경로가 공유하도록 한다. 정상 캐시 기준은 60초로 일치시킨다. 서버에서도 공개 데이터의 공유 캐시·동시 요청 병합을 검토한다.

### 3. P1 — 1,000대의 기본 조회량과 시작 시 요청 집중에 대한 운영 합의가 필요함

근거: `Sources/ZCRECore/Monitor.swift:52`, `Sources/ZCREBunny/CompanionStore.swift:164`, `Sources/ZCREBunny/Resources/ReadSnapshot.js:86`.

정상 응답, 계정별 목록 한 페이지, 추가 작업 조회 없음, 무변경 상태 기준의 산술 추정이다.

| 경로 | 1,000대 평균 요청/초 | 시간당 총 요청 |
| --- | ---: | ---: |
| 작업, 5초 | 200 | 720,000 |
| 잔액, 60초 | 16.7 | 60,000 |
| 공개 상태, 창이 열린 경우 60초 | 0–16.7 | 0–60,000 |
| 합계 | 약 217–233 | 780,000–840,000 |

가입 사용자 1,000명이 아니라 **연결된 앱 1,000대가 동시에 깨어 있는 상황**이다. 이 숫자는 최대치가 아니다. 1,000개를 넘는 이력이 있는 계정의 최초 조회는 목록 20회와 잔액 1회이며, 이런 계정 1,000대가 동시에 연결하면 초기 조회 묶음만 총 21,000회가 된다. 페이지는 각 앱에서 순차 요청된다. 시작·깨우기·실패 복귀에 시점 분산이 없어 같은 시점에 사용자가 몰릴 수 있다.

권장: 사용자당·IP당 제한, 인증 비용, DB 조회 비용, 예상 동시 접속 수를 운영팀과 합의한다. 시작/복구 시점을 분산해 피크를 낮추고 장기적으로 계정별 변경분·요약 응답 또는 작업 이벤트를 제공한다. 이벤트가 없는 상태에서 5초 감지 목표와 기본 작업 조회량을 동시에 크게 낮출 수는 없다. 실제 서버 용량을 모르는 상태에서 부담이 없다고 결론 내리지 않는다.

### 4. P2 — 오래된 미완료 작업·수동 새로고침이 기본선보다 요청을 늘림

근거: `Sources/ZCREBunny/Resources/ReadSnapshot.js:101`, `Sources/ZCRECore/Monitor.swift:19`, `Sources/ZCREBunny/DashboardView.swift:181`, `Sources/ZCREBunny/CompanionStore.swift:153`.

최신 목록 밖의 미완료 또는 알 수 없는 상태는 ID별 추가 GET으로 조회한다. 추적 중인 오래된 작업 3개이면 매 주기 목록 1회와 개별 3회로 작업 요청이 4배가 된다. 목록의 20페이지 제한은 개별 ID 조회 수를 제한하지 않는다. 전체 시간 제한은 있지만 개별 조회 개수 제한은 없다. 영구적으로 알 수 없는 상태가 남는 경우 장기 추적 비용도 검토해야 한다.

상세 현황의 수동 새로고침은 진행 중 중복만 막으므로 빠른 응답 뒤 연속 클릭하면 5초보다 자주 작업·잔액을 요청할 수 있다. 창 열기는 5초 병합이 있지만 잔액도 강제 갱신한다.

권장: 모든 활성 작업을 얻는 API 또는 ID 묶음 조회, 수동 갱신 최소 간격, 작업·잔액의 신선도 분리를 검토한다. 임의로 오래된 미완료 작업을 버리면 완료 감지가 사라지므로 서버 상태 계약을 먼저 확인한다.

### 5. P2 — 숨겨진 로그인 페이지와 SDK 요청은 앱 폴링 계측 밖에 있음

근거: `Sources/ZCREBunny/WebSession.swift:43`, `Sources/ZCREBunny/WebSession.swift:67`.

로그인 창을 숨겨도 `/credits` 페이지와 Clerk 세션은 남는다. 앱 폴링을 멈추는 것만으로 웹 페이지 자체의 타이머·인증 갱신·분석·리소스 요청이 모두 멈춘다고 볼 수 없다. 매 주기의 `getToken()`도 SDK 캐시 적중 여부를 실측하지 않았으므로 매번 인증 HTTP 요청이 발생한다고 단정하지 않는다.

권장: 요청 경로별 개수·응답 시간·전송량을 인증값·개인정보 없이 계측하고 앱 폴링과 웹 페이지 트래픽을 구분한다. 공식 앱 인증 방식이 마련되면 전체 웹 페이지 유지 비용을 제거할 수 있다. 로그인 기능을 깨뜨릴 수 있는 웹 리소스 일괄 차단은 하지 않는다.

## 서비스 부하와 별도로 남은 정확도 조건

- 잔액 경로에서 받은 Retry-After도 전체 계정 폴링 대기에 적용된다. 제한이 계정 전체인지 엔드포인트별인지에 따라 작업 감시 지연이 필요 이상으로 길어질 수 있다. 근거: `Sources/ZCREBunny/WebSession.swift:128`. 서버 계약 확인 후 분리 여부를 정한다.
- 현재 상태 전이 후 15초 확인 구간보다 정산이 늦으면 평소 60초 확인까지 잔액 반영이 늦을 수 있다. 잔액 버전·정산 완료 표식이 필요하다.
- 최초 1,000개 제한 밖에 있는 미확인 활성 작업은 ID를 아직 몰라 직접 추적할 수 없다. 잘림 표시가 있지만 모든 활성 작업 발견을 보장하지 않는다.
- 작업 상세 404는 추적 종료를 위해 취소로 취급한다. 일시적 가시성 지연도 404로 반환하는 API라면 완료를 놓칠 수 있으므로 응답 계약 확인이 필요하다.
- 최소 필드만 네이티브에 넘기는 것은 정보 보관을 줄이지만 HTTP 응답 다운로드량을 줄이지는 않는다. 필드 선택·요약 응답은 서버 지원이 필요하다.

## 검증 및 재현

```sh
bash scripts/test.sh
node scripts/review-traffic.mjs
```

- Swift 코어 40개 + 앱 22개 = 62개, JavaScript 브리지 32개 통과.
- 모의 트래픽 수치는 `docs/reviews/2026-10-26-traffic-simulation.json`에 보관했다. 네 가지 조건을 실제 브리지 코드로 실행하며 네트워크는 모두 대역 처리한다.
- 주석 작업 직후 기존 코드 50개 파일의 독립 주석 줄을 제거한 텍스트가 백업과 일치했다. 그 이후 동작 변경은 효과음·설정·번들 등록 및 앱 버전 갱신이며 HTTP/상태 감시 실행 코드는 변경하지 않았다.
- 실계정 생성, 실제 완료/정산, 서비스 운영 부하·배터리·장시간 오디오 재생 검증은 실행하지 않았다. 테스트 통과는 운영 부하가 없다는 증명이 아니다.

이 검토는 발견한 조건과 우선순위를 정리한 것이며 위의 트래픽 개선을 이미 반영했다는 뜻은 아니다. 후속 최적화에서 5초 목표, 동일 작업 수에서의 교체 감지, 계정 분리, 숨김 중 감시는 유지해야 한다.
