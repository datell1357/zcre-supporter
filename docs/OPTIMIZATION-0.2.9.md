# 0.2.9 조회·화면 최적화

2026-10-26, ZCRE 서포터 0.2.9 (11). 0.2.8 소스 전달본과 비교했다. 클라이언트가 제어할 수 있는 중복 요청과 반복 계산을 줄였으며, 서버 API·요금제·인증 권한은 변경하지 않았다.

## 유지한 동작

- 정상 작업 조회는 작업 유무와 관계없이 시작 기준 약 5초다. 느린 요청은 겹치지 않으며 완료 후 최소 1초를 둔다. 실제 지연에는 서버 응답 시간이 더해진다.
- 작업 개수만 비교하지 않고 ID와 상태를 확인한다. 목록 밖 미완료 작업의 개별 조회, 60초 겹침 조회, 처음 연결의 최대 1,000개 범위 표시를 유지한다.
- 잔액은 기본 60초이며 작업 변화 시 바로 확인하고 15초 동안 후속 정산을 확인한다. 별도 크레딧 사용도 다음 정기 조회에서 확인한다. 계정 조회 실패·서버 제한 중에는 정상 5초를 보장할 수 없다.
- 동시 생성 개수·지크·상단 바는 동일한 API 스냅샷을 사용한다. 웹 DOM의 오래된 사용 개수는 사용하지 않고 요금제 한도만 사용한다.
- 지크 숨김은 모션·산책·효과음을 멈추며 데이터 감시는 유지한다. 완료·실패 알림, 모션 원본과 목덜이 기준점, 효과음 및 설정은 유지한다.

## 반영한 변경

1. **대량 이력의 잘못된 변경 감지 제거**: 표시용 종료 이력 50개와 변경 감지 기록을 분리했다. 변경 기록은 메모리에만 최대 10분·10,000개로 제한한다. 계정·세션·네이티브가 실제 반영한 응답 번호가 모두 일치해야 재사용한다. 실패·취소·거부된 응답은 다음 호출의 판단 근거로 쓰지 않는다.
2. **목록 페이지 크기 조정**: 평소에는 20개, 이미 확인한 최근 겹침 구간이 20개를 넘으면 기존에 지원하는 50개 단위를 사용한다. 하나의 조회 안에서는 크기를 고정하고 페이지 제한·중복 커서 차단·개별 미완료 조회를 유지한다.
3. **계정 새로고침 통합**: 현황 열기·수동·자동 갱신이 같은 다음 허용 시각을 공유한다. 창을 열 때 신선한 잔액을 강제로 읽지 않는다. 상세 현황의 명시적 새로고침은 잔액 갱신 의도를 유지하면서 최소 5초와 서버의 대기 시간을 지킨다.
4. **복귀 시점 분산**: 로그인 준비·네트워크 복구·잠자기 복귀를 0~1초 분산하고 실패 재시도도 최대 20% 분산한다. 정상 5초 주기는 늘리지 않는다. 일반 오류 지연 상한은 300초이며 서버가 더 긴 대기를 지정하면 존중한다.
5. **공개 상태 요청 통합**: 현황창이 열린 동안 자동 조회하며 정상 응답 후 60초 캐시를 재개방에도 사용한다. 수동 갱신은 최소 5초, 실패는 30~300초 지연, Retry-After의 초·HTTP 날짜를 반영한다. 오프라인·창 닫힘·잠자기에는 중단한다. 캐시와 재시도 시각은 닫아도 유지한다.
6. **공개 상태 조건부 요청**: 서버가 ETag/Last-Modified를 제공한 경우만 If-None-Match/If-Modified-Since를 사용한다. 유효한 304는 본문을 재사용한다. 집계 자체의 calculated_at은 바꾸지 않아 오래된 정상 상태를 정상으로 오인하지 않는다. 검증자를 제공하지 않는 서버에는 일반 GET을 유지한다. 실제 서버의 304 지원 여부는 확정하지 않았다.
7. **반복 계산·화면 변경 축소**: 불변 스냅샷의 진행 작업 목록을 한 번 계산한다. 알림 이력은 로컬에서 합친 최종 목록이 바뀔 때만 화면 상태에 반영하며, 보관 한도 밖의 오래된 이력은 해시·알림 객체 생성 전에 제외한다. 기존 알림의 ID·읽음 상태를 보존한다.

## 모의 요청 수 비교

`scripts/review-traffic.mjs`가 실제 ReadSnapshot.js를 격리 문맥에서 실행한다. 모든 fetch는 모의 응답이며 운영 서버 부하 시험이 아니다. 비교 원본은 보존된 0.2.8 전달본이다.

| 조건 | 0.2.8 | 0.2.9 |
| --- | --- | --- |
| 정상 1시간, 최초 연결 제외 | 작업 720 + 잔액 60 | 작업 720 + 잔액 60 |
| 최초 이력 1,001개 | 작업 20 + 잔액 1 | 작업 20 + 잔액 1 |
| 최신 목록 밖 미완료 3개, 한 주기 | 작업 4 | 작업 4 |
| 최근 종료 60개 + 옛 이력 20개, 5초 간격 6회 | 작업 24 + 잔액 6 = 30 | 작업 12 + 잔액 3 = 15 |

마지막 조건에서는 요청이 50% 감소했다. 최초 감지 후 정산 확인 3회는 유지하며, 이후 같은 이력으로 잔액 확인을 반복하지 않는다. 별도 회귀 검사에서는 캐시를 준비한 대량 이력의 안정 구간에서 잔액 추가 요청이 0회임을 확인했다. 이 비율을 모든 사용자의 데이터 사용량·배터리 감소율로 일반화할 수 없다.

결과 파일: `reviews/2026-10-26-optimization-traffic-before.json`, `reviews/2026-10-26-optimization-traffic-after.json`.

## 검증

- `bash scripts/test.sh`: Swift 80개, JavaScript 39개 통과
- 상태 전이·동일 개수의 작업 교체·오래된 미완료 추적·Decimal 잔액·계정 전환·실패 후 복구·대량 이력 캐시·미반영 응답·TTL/항목 상한 회귀 검사
- URLProtocol 대역으로 공개 상태의 60초 재개방 캐시, 수동 병합, 429/503 및 Retry-After, 유효/무효 304, 오래된 집계, 오프라인과 취소 응답 검사
- 기존 8방향 이동·드래그 기준점·모션 우선순위·작업 중 산책 정지·효과음 중복/음소거 검사 유지
- 실제 운영 서버의 대량 호출, 유료 생성, 실제 완료 알림 발송, 장시간 전력·네트워크 계측은 실행하지 않았다. 로컬 모의 검증을 실제 서버 성능 보장으로 해석하지 않는다.

## 서버 협의가 필요한 부분

정상 1,000대가 모두 온라인이면 작업 조회만 약 200요청/초다. 잔액 기본 조회까지 약 217요청/초이며 모든 현황창이 열려 있으면 공개 상태까지 약 233요청/초다. 초기 페이지·오래된 진행 작업·상태 전이 후 정산·Clerk 및 웹 페이지 자체 요청은 별도다. 페이지별 응답 크기·인증 비용·DB 비용·실제 동접률에 따라 실제 부담은 달라진다.

공식 앱 인증, 전체 활성 작업/변경분/묶음 조회, 서버 이벤트(SSE 등), 정산 완료 표식·잔액 버전, 요청 제한 범위, 404의 업무적 의미, 공개 상태의 CDN 캐시는 운영팀과 API 계약을 확인한 뒤 도입해야 한다. 지원을 확인하지 않은 엔드포인트를 만들거나 미완료 감시를 생략하지 않았다. 숨겨진 웹 페이지의 인증·자체 요청과 모션 리소스 해상도·원본 프레임은 유지했다.

로컬 ad hoc 빌드와 Apple 공증을 구분한다. 공증·지원 macOS/Intel 실기기 검증·실제 작업 정산 및 알림의 종단 간 확인은 정식 공개 전 남은 조건이다.

사용자 후속 요청으로 좌우 작업 자세·실패 울음 모션과 타자음 양보를 추가했다. 이 기능 변경은 [모션·오디오 기록](MOTION-AUDIO-0.2.9.md)에 별도로 정리했다.
