# 트래픽 최적화 재검토

검토일: 2026-10-25, 앱 0.2.7 소스 기준. 이번 작업은 검토이며 앱 코드를 변경하거나 실행 중인 설정을 바꾸지 않았다.

## 결론

작업 시작·진행·완료 감지를 위한 5초 목표 주기는 유지한다. 크레딧은 평소 60초와 실제 작업 전환 시, 공개 서비스 상태는 현황판이 열린 동안 60초로 유지한다. 지크 숨김은 데이터 조회 중지 조건으로 사용하지 않는다.

앱에서 먼저 줄일 것은 중복 판정과 부가 요청이다. 정상 대기 상태의 작업 조회 자체는 이미 한 주기 한 요청이므로, 1,000대가 각자 5초마다 확인하는 기본 200 요청/초를 크게 줄이려면 ZCRE가 변경분 또는 이벤트를 제공해야 한다. 응답 크기 절감과 요청 횟수 절감, 운영 서버의 DB 부하 감소는 구분한다.

## 현재 동작과 검증

| 항목 | 현재 동작 | 근거 |
| --- | --- | --- |
| 작업 | 유무와 관계없이 5초 목표 주기, 느린 조회와 중첩하지 않음 | `Monitor.swift:46`, `CompanionStore.swift:148` |
| 크레딧 | 60초, 신규 작업/상태 전환 즉시, 이후 15초 후속 확인 | `ReadSnapshot.js:99` |
| 현황 카드 열기 | 5초보다 오래된 스냅샷이면 작업+크레딧 강제 갱신 | `CompanionStore.swift:138` |
| 초기 이력 | 50개씩 최대 20페이지, 최대 1,000개 | `ReadSnapshot.js:75` |
| 후속 이력 | 20개씩, 최근 60초 중복 범위를 포함하는 페이지 조회 | `ReadSnapshot.js:76` |
| 오래된 미완료 작업 | 최신 조회에 없으면 ID별 추가 GET | `ReadSnapshot.js:89` |
| 보관 | 최근 완료 50개와 미완료 작업 유지 | `WebSession.swift:70`, `ReadSnapshot.js:117` |
| 공개 상태 | 열려 있을 때 60초, 다시 열 때 캐시 30초 이상이면 조회 | `ServiceStatusStore.swift:40` |
| HTTP 캐시 | 작업/크레딧 `no-store`, 공개 상태 URLCache 없음 | `ReadSnapshot.js:38`, `ServiceStatusStore.swift:24` |
| 인증 페이지 | 숨겨진 WebKit `/credits` 페이지로 로그인 세션 유지 | `WebSession.swift:39` |

기존 웹 브리지 테스트 32개가 통과했다. 추가로 실제 `ReadSnapshot.js`를 가상 시계와 모의 응답으로 실행해 다음을 확인했다. 운영 계정의 과금 작업이나 운영 서버 부하 테스트는 하지 않았다.

| 모의 조건 | 관찰 |
| --- | --- |
| 정상·무변경 한 시간, 초기 연결 제외 | 작업 720회 + 크레딧 60회 |
| 1,000개보다 많은 과거 이력으로 첫 연결 | 작업 20회 + 크레딧 1회 |
| 최신 20개 밖에 이미 추적 중인 미완료 작업 3개 | 한 주기에 목록 1회 + 개별 상태 3회 |
| 60초 중복 조회 범위에 완료 작업 60개, 변경 없이 5초 간격 6주기 | 목록 24회 + 크레딧 6회 |

마지막 조건에서는 메모리에 남기는 완료 기록 50개와 중복 조회 범위가 맞지 않는다. 보관에서 빠진 완료 기록이 다시 응답에 나타나면 `changed`가 참이 되어 실제 상태 변화가 없어도 크레딧 후속 확인 구간이 갱신된다. 모의 대량 이력에서 재현한 조건이며 현재 사용자의 계정에서 상시 발생한다고 확인한 것은 아니다.

공개 상태 API는 한 번만 실제 GET으로 확인했다. 본문 전송 1,528 bytes, 응답 헤더 2,751 bytes, 압축 해제 본문 23,573 bytes, 모델 9개였다. `Cache-Control: public, max-age=0`, `Age: 0`, `x-vercel-cache: MISS`, gzip이었으며 ETag/Last-Modified는 없었다. 이 응답 하나로 서버 내부 집계 캐시나 전체 CDN 적중률까지 판단할 수는 없다.

## 1,000대 기준 해석

정상 응답·목록 한 페이지·추가 개별 작업 없음·무변경을 가정하면 다음과 같다.

| 경로 | 1,000대 평균 요청/초 | 전체 시간당 요청 |
| --- | ---: | ---: |
| 작업 | 200 | 720,000 |
| 크레딧 | 16.7 | 60,000 |
| 공개 상태 | 0–16.7 | 0–60,000 |
| 합계 | 약 217–233 | 780,000–840,000 |

이는 기본선이지 최대치가 아니다. 각 계정에 목록 밖 미완료 작업이 3개라면 작업 경로만 800 요청/초가 된다. 동시 첫 연결, 추가 페이지, 크레딧 전환/후속 확인, 카드 재개방, WebKit 페이지/인증 요청은 별도다. 사용자 1,000명 가입과 로그인한 앱 1,000대 동시 실행도 구분한다.

## 권장 실행 순서

### 1. 앱에서 우선 정리

1. **변경 감지용 기록을 화면 표시용 50개 목록과 분리한다.** 최근 조회 중복 범위와 지연 도착 여유 동안 이미 확인한 ID/상태를 별도로 유지한다. 미완료 작업은 삭제하지 않는다. 계정 변경 시 분리·초기화하고, 같은 개수에서 완료와 시작이 교체되는 경우도 잡는다. 목표는 모의 대량 이력에서 불필요한 잔액 조회를 없애는 것이다.
2. **현황판 재개방 시 잔액 강제 갱신을 분리한다.** 작업은 5초 신선도 기준, 크레딧은 마지막 성공 조회 시각과 전환/정산 필요 여부 기준으로 판단한다. 명시적 새로고침과 실제 작업 상태 전환은 즉시 조회를 유지한다. 단순 창 열기로 이미 신선한 잔액을 반복 요청하지 않는다.
3. **공개 상태의 열기 기준을 30초에서 60초로 통일한다.** 현재 페이지 내 메모리 캐시를 활용하고, 연속 클릭·재개방을 합친다. 오류 시에는 재시도 대기와 Retry-After를 적용해 창을 반복 열어도 요청이 폭주하지 않도록 한다. 정상 타이머 60초, 창 닫기 중지는 유지한다.
4. **시작·복귀·실패 재시도 시점을 분산한다.** 5초 작업 목표를 지키는 범위에서 초기 시점과 재연결을 분산한다. 정상 호출 수는 줄지 않지만 사용자들이 동시에 접속할 때 몰림을 줄인다. 새 타이머를 여러 개 만들지 않고 기존 스케줄러에 합친다.
5. **실제 네트워크 계측을 추가한다.** 엔드포인트별 요청 수·압축 전송 바이트·응답 시간·상태 코드만 집계한다. 인증값, 프롬프트, 결과 URL, 계정 식별자는 기록하지 않는다. WebKit 자체 요청을 앱의 명시적 폴링과 구분한다.

현재 단일 조회 중복 방지, 60초 잔액 재사용, 잠자기/오프라인 중지, 작업 경로의 오류 백오프는 이미 있으므로 새 절감 효과로 중복 계산하지 않는다.

### 2. ZCRE 서버와 함께 줄일 부분

1. **계정별 요약/변경분 API:** 모든 활성 작업, 바뀐 작업의 ID·상태·버전, 확정 잔액/예약량·잔액 버전, 동시 생성 한도를 작은 응답으로 제공한다. 서버 발급 커서 또는 단조 증가 버전과 변경 이력을 사용해 시작 후 5초 안에 끝난 작업도 놓치지 않는다. 최신 작업 몇 개나 개수만 반환하는 방식으로는 충분하지 않다.
2. **초기 전체 이력 지연 로딩:** 최신 10–20개와 모든 활성 작업을 먼저 읽고 과거 이력은 상세 현황에서 추가한다. 현재 API 계약에서는 모든 활성 작업을 별도로 받는 방법을 확인하지 못했으므로 단순히 첫 페이지에서 끊는 변경은 하지 않는다. 계정 확인 후 안전하게 저장된 커서를 재사용하는 방식도 검토한다.
3. **공개 상태 CDN 캐시:** 사용자와 무관한 상태 데이터에 30–60초 공유 캐시, 동시 캐시 미스 요청 병합, ETag를 적용한다. 필요하면 상태 요약 전용 응답을 제공한다. 현재도 본문은 gzip 약 1.5 KB이므로 필드 축소만으로 큰 네트워크 절감을 약속하지 않는다. 개인 작업·크레딧은 공용 캐시에 넣지 않는다.
4. **작업 이벤트 구독:** 서버의 실제 작업/정산 이벤트를 SSE 등으로 보내고 연결 복구 시 이벤트 ID와 변경분을 재확인한다. 건강한 연결에서는 잦은 작업 폴링을 대체하고, 끊기면 5초 폴링으로 복구한다. 이벤트만 놓친 경우를 잡는 저빈도 대조도 필요하다. 운영상 연결 유지·인증·하트비트 비용을 함께 검증한다.
5. **앱 전용 인증/API:** 공식 인증 계약을 마련하면 숨겨진 전체 웹 페이지를 유지하는 방식을 대체할 수 있다. 단순히 MCP 호출로 바꾸는 것만으로 5초 요청 수가 감소하거나 작업 이벤트가 제공되는 것은 아니다. 현재 연결 도구의 개별 작업 `wait_seconds`는 아직 모르는 새 작업 전체를 발견하는 대체 수단이 아니다.

ETag/304는 주로 응답 본문을 줄인다. 조건부 요청 자체는 남고, 서버가 매번 DB를 읽어 ETag를 계산하면 DB 부하는 그대로일 수 있다. 공유 캐시도 각 CDN 캐시 위치/키별로 동작하므로 "1,000명이어도 전 세계 원본 요청은 분당 1회"로 보장하지 않는다. 다른 중계 서버가 사용자별 5초 폴링을 그대로 수행하는 것도 ZCRE 요청 총량을 줄이지 못한다.

## 정확도와 검증 기준

- 시작·완료·실패·취소, 동일 작업 수에서 작업 교체, 5초 이내 생성/완료, 오래된 활성 작업, 50개보다 많은 최근 완료 이력을 검증한다.
- 크레딧 차감·예약·환불·정산은 서버 값으로 확인한다. 같은 잔액이 두 번 나왔다는 이유만으로 지연 정산이 끝났다고 판단하지 않는다. 현재 15초 후속 조회도 그보다 늦은 정산을 보장하지 않으므로 잔액 버전/정산 상태가 가장 확실한 개선이다.
- 작업·크레딧·서비스 상태의 오류와 신선도를 구분한다. 현재 크레딧 경로의 Retry-After도 전체 작업 폴링 대기에 반영된다. 제한이 계정 공통인지 엔드포인트별인지 서버 계약을 확인한 뒤 각각의 재시도 정책을 결정한다.
- 오류를 작업 0개·잔액 0으로 바꾸지 않고 마지막 확인 시각과 지연 상태를 표시한다. 숨김 상태에도 데이터와 완료 감지는 계속 유지한다.
- 절감 전후에 실제 작업 시작/진행/완료와 UI 세 곳의 일치를 확인하고, 동일 조건에서 요청 수·압축 바이트·CPU/깨우기를 비교한다. 현재 사설 API 응답 바이트, 서버 DB 비용, 배터리 절감률은 측정하지 않았다.
