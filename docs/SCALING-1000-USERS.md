# ZCRE 서포터 1,000명 동시 실행 시 요청량

2026-10-25 현재 소스에 근거한 계산이다. ZCRE 운영 서버의 처리 용량이나 한도를 측정한 결과가 아니다.

## 기본 요청 수

가입자 수가 아니라 앱을 켜고 로그인한 **동시 실행 1,000대**를 가정한다. 정상 응답, 작업 목록 한 페이지, 추가 작업 조회 없음, 무변경 상태가 기준이다.

| 조회 | 한 사용자 | 1,000대 평균 | 시간당 |
| --- | --- | --- | --- |
| 작업 목록 | 5초마다 | 200 요청/초 | 720,000회 |
| 크레딧 | 60초마다 | 16.7 요청/초 | 60,000회 |
| 공개 서비스 상태 | 메뉴가 열린 동안 60초마다 | 모두 열었을 때 16.7 요청/초 | 최대 60,000회 |
| 기본 합계 | | 216.7–233.3 요청/초 | 780,000–840,000회 |

24시간 같은 상태라면 약 1,872만–2,016만 회다. 서비스 상태는 열 때 30초 이상 오래된 캐시도 새로 읽으므로 메뉴 재개방과 수동 새로고침은 별도로 더해질 수 있다. 잠자기·오프라인·로그아웃·오류 대기 중인 사용자는 이 정상 상태 가정에서 제외된다.

작업 상태가 바뀌면 크레딧을 즉시 읽고 이후 15초간 5초 주기로 후속 정산을 확인한다. 작업 목록 추가 페이지, 최근 목록 밖의 미완료 작업 개별 조회, 웹 페이지 로딩·Clerk 인증 갱신도 별도다. 첫 연결은 작업 이력 최대 20페이지와 잔액 1회를 읽으므로, 1,000대가 함께 처음 연결하면 최대 약 21,000회의 초기 조회가 짧은 기간에 추가될 수 있다. 실제 요청 수와 소요 시간은 계정의 이력과 응답 속도에 따라 달라진다.

## 바이트와 서버 부담

현 버전의 압축 전송 바이트는 실측하지 않았다. 0.2.4의 시간당 2.8 MB 측정값은 폴링 간격과 페이지 크기가 달라 현재 버전에 그대로 적용할 수 없다.

예를 들어 작업 응답의 실제 전송 본문이 평균 5 KB라면 작업 조회만 약 3.6 GB/시간, 20 KB라면 약 14.4 GB/시간이다. 이는 예시이며 요청/응답 헤더, TLS, 잔액·상태·인증 등은 제외했다. 전송량보다 더 먼저 병목이 될 수 있는 것은 각 요청의 인증과 DB 조회 비용, DB 연결 수, 인덱스 및 캐시 적중률이다. 현재 클라이언트 소스로 ZCRE의 내부 비용과 처리 여유를 알 수 없다.

애니메이션은 번들 스프라이트의 로컬 재생이다. 새 달리기·불꽃·타이핑 모션은 서버 요청이나 영상 다운로드를 추가하지 않는다. 움직이는 동안의 앱 CPU/GPU 사용은 별도로 확인해야 한다.

## 배포 전 권장 순서

1. 5초 감지 주기는 유지하고 앱 시작·복귀·오류 재시도 시점을 분산한다. 평균 요청 수는 그대로지만 동시 몰림을 줄인다. 기존 백오프와 Retry-After는 유지한다.
2. 초기 전체 이력은 현황 표시와 분리한다. 최신·활성 작업부터 읽고 과거 이력은 상세 창에서 지연 로딩한다. 모든 활성 작업을 반환하는 서버 계약을 확보해야 오래된 미완료 작업을 놓치지 않는다.
3. ZCRE와 협의해 작은 상태 요약 또는 변경분 API를 만든다. 작업 ID·상태·수정 버전·동시 사용량과 필요한 잔액만 반환하고, 서버에서 계정별로 안전하게 캐시한다. ETag/304는 본문을 줄이지만 요청 자체나 DB 비용을 자동으로 없애지는 않는다.
4. 모든 사용자에게 같은 공개 서비스 상태는 서버/CDN에서 공용 캐시한다. 개인 작업·크레딧은 공용 캐시에 섞지 않는다.
5. 장기적으로 작업 이벤트에 연결된 SSE/WebSocket을 제공하면 변경 시 전송하고 폴링은 복구용으로 쓸 수 있다. 단순히 중계 서버가 1,000계정을 대신 5초마다 조회하는 구조는 ZCRE 요청 총량을 줄이지 못한다.
6. 운영팀이 허용한 테스트 환경에서 1,000대 모델과 시작·복귀 몰림을 검증하고, p95/p99 응답 시간·429/5xx·DB 조회/연결·전송량·비용을 확인한 뒤 배포 규모를 결정한다. 이번 검토에서 운영 서버 부하 테스트는 수행하지 않았다.
